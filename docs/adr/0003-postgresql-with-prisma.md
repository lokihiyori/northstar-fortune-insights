# ADR 0003: PostgreSQL with Prisma, including vector search

- **Status:** Accepted
- **Date:** 2026-08-04
- **Phase:** 0

## Context

NorthStar's data is strongly relational and consistency-sensitive. A guidance report has versions,
each version has paths, each path has reasons and citations, and citations point at source chunks
that must still exist. Usage metering and subscription state have to agree with each other or a user
is billed wrongly. These are foreign keys and transactions, not documents.

The retrieval layer (spec section 9) adds a second requirement: similarity search over embedded
source chunks. That is normally an argument for a dedicated vector database.

## Decision

**PostgreSQL is the single durable store**, accessed through **Prisma**, with the `pgvector`
extension providing similarity search.

Rationale for one store rather than two:

- Retrieval must filter on `status = PUBLISHED`, region, and topic before ranking by similarity
  (spec section 9). With a separate vector store this becomes a two-system join kept in sync by
  application code. In Postgres it is one query with a `WHERE` clause.
- A citation and the chunk it cites can be written in the same transaction, so a report can never
  reference a chunk that was not committed.
- At this corpus size (curated, human-reviewed sources — tens of thousands of chunks, not millions),
  pgvector is comfortably fast enough. A dedicated vector database would be solving a scale problem
  the product does not have.

Supporting decisions:

- **Prisma 7** with the `prisma-client` generator, output to `src/generated/prisma` (gitignored,
  regenerated by `postinstall`). Chosen over a hand-rolled query layer for typed access and a real
  migration history; chosen over Drizzle because migration ergonomics and Studio matter more here
  than raw query control.
- **Migrations are the only schema mechanism.** No `db push` against a database that matters.
- **Extensions are created by the container, not by a migration** — see
  `docker/postgres/init/01-extensions.sql`. Managed Postgres providers vary in whether a migration
  role may `CREATE EXTENSION`, so keeping it in provisioning avoids a migration that works locally
  and fails on deploy.
- `DIRECT_DATABASE_URL` is reserved for migrations against a pooled host (PgBouncer, Supabase,
  Neon), where the pooled connection cannot run DDL.

## Consequences

**Positive**

- One backup, one restore, one connection string, one consistency model.
- Retrieval filters and similarity ranking compose in SQL.
- Schema history is reviewable in `prisma/migrations`.

**Negative**

- pgvector index tuning (IVFFlat/HNSW list and probe settings) becomes the project's problem at
  larger corpus sizes. Acceptable at the intended scale, and revisitable without changing the
  application's data model.
- The generated client is a build artifact, so a fresh clone must run `pnpm install` (which triggers
  `prisma generate`) before typecheck will pass. This is documented in the README.

**Phase 0 status:** the schema contains only a placeholder `User` model, enough to exercise
generate/migrate/seed. Phase 2 extends it to the Auth.js adapter shape; later phases add the entities
in spec section 10.
